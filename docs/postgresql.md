# Carga no PostgreSQL

Além de SQLite e CSV, o `cnpj.py` grava direto no PostgreSQL:

```bash
python3 cnpj_full/cnpj.py dados/2026-10 postgres --dir                # carga completa + chaves e índices
python3 cnpj_full/cnpj.py dados/2026-10 postgres --dir --noindex      # sem chaves e índices no fim
python3 cnpj_full/cnpj.py dados/2026-10 postgres --dir --continuar    # retoma uma carga interrompida
```

Não há `<pasta saída>`: a conexão vem do `.env` (ou de variáveis de ambiente).

## Configuração (.env)

Copie o `.env.example` para `.env` na raiz do projeto e ajuste:

Variável | Descrição | Padrão
-------- | --------- | ------
`CNPJ_DB_HOST` | Servidor do PostgreSQL | `localhost`
`CNPJ_DB_PORTA` | Porta | `5432`
`CNPJ_DB_NOME` | Banco de dados. **Se não existir, é criado** (UTF-8), se o usuário tiver permissão | `dados_rfb`
`CNPJ_DB_USUARIO` | Usuário | `postgres`
`CNPJ_DB_SENHA` | Senha | vazio
`CNPJ_DB_SCHEMA` | Schema das tabelas (criado se não existir) | `dados_rfb`

Variáveis já definidas no ambiente (ex: `environment:` do docker-compose, `export` no Linux, `set` no Windows) têm prioridade sobre o `.env`. Para usar um `.env` em outro lugar, informe o caminho em `CNPJ_ENV`.

Driver: `psycopg` 3 (já está no `requirements.txt` como `psycopg[binary]`, com binários para Windows, Linux e macOS; não precisa instalar o cliente do PostgreSQL).

## Subindo um PostgreSQL para teste com Docker

```bash
docker run -d --name cnpj-pg -e POSTGRES_PASSWORD=cnpj -p 5432:5432 -v cnpj-pg:/var/lib/postgresql/data postgres:16
```

E no `.env`: `CNPJ_DB_HOST=localhost`, `CNPJ_DB_USUARIO=postgres`, `CNPJ_DB_SENHA=cnpj`. Se o CNPJ-full também rodar em container na mesma rede do Docker, use o nome do serviço/container no `CNPJ_DB_HOST` (ex: `cnpj-pg`), não `localhost`.

## Modelo

Tabelas, colunas e tipos seguem o modelo do cnpjrfb ([`modelo_postgres.sql`](https://github.com/bjverde/cnpjrfb/blob/nextversion/docs/modelo_banco/postgresql/modelo_postgres.sql)), no schema `dados_rfb`, para o sistema web ler o mesmo banco:

* códigos de domínio (município, país, CNAE, natureza, qualificação, motivo...) como `INTEGER`;
* datas como `DATE` (`20200101` vira `2020-01-01`; data zerada ou inválida, ex: `20241399`, vira NULL);
* `capital_social` como `NUMERIC(18,2)`;
* `situacao_cadastral` e `porte_empresa` como texto de 2 dígitos (`02`, `05`);
* `socios` ganha a coluna `id` (`BIGINT GENERATED BY DEFAULT AS IDENTITY`), como no cnpjrfb;
* textos como `TEXT` (no PostgreSQL tem o mesmo desempenho de `VARCHAR`), para que um valor maior que o previsto no modelo não interrompa a carga.

Os demais tratamentos (datas zeradas, capital com vírgula, representante legal zerado) são os mesmos do SQLite, descritos em [Carga](carga.md#tratamentos-feitos-na-carga).

A carga **apaga e recria** as tabelas do schema (com `DROP TABLE ... CASCADE`, o que também remove chaves estrangeiras criadas pelo `modelo_postgres_fk.sql`). A tabela `controle_carga` também é recriada.

## Como a carga funciona

* Os dados entram com `COPY ... FROM STDIN` (o método mais rápido do PostgreSQL), em blocos de 200.000 linhas, sem chaves e sem índices.
* Cada arquivo da RF (ex: `Estabelecimentos3.zip`) é gravado em **uma transação**, junto com o seu registro na `controle_carga`. Se a carga for interrompida (erro, Ctrl+C, queda), o PostgreSQL desfaz só aquele arquivo, e `--continuar` sempre pode retomar. Por isso não existe `--seguro` no PostgreSQL: a carga já é segura.
* A verificação das quantidades é a mesma do SQLite ([Verificação da carga](carga.md#verificação-da-carga)); `registros_gravados` é o total que o `COPY` informou.
* No fim (sem `--noindex`) são criadas as chaves primárias do modelo do cnpjrfb (`pk_empresa`, `pk_estabelecimento`, `pk_simples`, `pk_socios` e as das tabelas de domínio) e os índices de `socios` (`cnpj_basico`, `cpf_cnpj_socio`, `nome_socio_razao_social`), seguidos de `ANALYZE`. Se uma chave primária não puder ser criada (ex: CNPJ repetido no arquivo da RF), o script avisa e cria um índice comum no lugar.

Para conferir depois:

```sql
SELECT arquivo, tabela, registros_lidos, registros_gravados, status, observacao
FROM dados_rfb.controle_carga;
```

## Outros SGBDs

A carga por SGBD fica em `cnpj_full/sgbd/`. Cada SGBD é um módulo com uma classe `Destino` com a mesma interface (`cria_tabelas`, `prepara_continuacao`, `grava_arquivo`, `verificacao`, `cria_indices`, `fecha`); o `postgres.py` serve de modelo. Os próximos (MySQL/MariaDB com `LOAD DATA`, SQL Server, Oracle) entram registrando o módulo em `cnpj_full/sgbd/__init__.py`.
